Lab · agent observability

Watch the agents work.

Real traces from the AI agents that built this site: every model call, allowlisted tool call and handoff, with code evaluators on top.

The data comes from OpenCode’s local session store on my machine, November 7–12, 2026, exported by a script that keeps structure and numbers only. Prompts, responses, file contents and commands are never published, and calls to tools outside an allowlist are dropped (24 of them). Model latency is estimated from message timings. The evaluators are code checks; there is no LLM judge. To keep the file small, most spans are merged into summary spans; the totals, percentiles and evaluator results use every span.

          Evaluators

          Seven deterministic checks, scored per trace on every span. A check only runs where it applies.

          1. Tool error rate

            Did the agents mostly call their tools correctly?

            Rule. Passes when 10% or fewer of the trace’s tool calls returned an error.

            58 pass · 3 fail · scored on 61 traces

            Eight traces made no tool call and are not scored. An error is any call the tool reported as failed; the export does not say why.

          2. Recovered after error

            When a tool call failed, did the agent retry or fix it?

            Rule. Passes when every failed call is followed, later in the same trace, by a successful call of the same tool.

            23 pass · 6 fail · scored on 29 traces

            Only traces with an error are scored. The match is by tool name, so any later successful call of that tool counts, even one that did something else: a pass is a weak signal, a fail is worth opening.

          3. Delegation used

            Did the orchestrator hand work to a specialist?

            Rule. Passes when the trace has at least one subagent run.

            28 pass · 41 fail · scored on 69 traces

            More a description than a quality bar: a short question or a plan doesn’t need a subagent, so many of these fails are fine.

          4. Review before commit

            Was the change reviewed before it was saved?

            Rule. Passes when a quality-reviewer run finished after the previous commit in the same session (or the start of the window) and before the trace’s last commit.

            Needs context. The check looks back only to the previous commit in the same session, so when a reviewed commit is followed by a quick “go ahead” turn that commits small fixes, that later commit has no review of its own and fails, even though the work around it was reviewed. Read the fails trace by trace before calling them gaps.

            10 pass · 18 fail · scored on 28 traces

          5. Tests before commit

            Were the tests run before the change was saved?

            Rule. Passes when a test command finished in that same window.

            27 pass · 1 fail · scored on 28 traces

            It shows that tests ran, not that they passed: the export keeps only each command’s category, never its output.

          6. Model latency budget

            Did the model respond quickly enough to keep the loop moving?

            Rule. Passes when the trace’s p90 model-step latency is under 30 s.

            62 pass · 7 fail · scored on 69 traces

            Latency is estimated from message timings, from a step’s start to the start of its last tool call; the store has no time to first token. A step that ends without a tool call runs to the end of its message, which pushes p90 up.

          7. Generated tokens per tool call

            How much did the model write for each action it took?

            Rule. Output plus reasoning tokens, divided by tool calls. A number, not pass or fail.

            Median 749 · range 165–2,951 · 61 traces

            Lower means terser actions. Cache reads are left out: they are context the model read again, not text it wrote.

          What this data is, and isn’t

          • Where it comes from. OpenCode, the coding agent I work in, keeps every session in a local database. A script reads it read-only and writes agent-traces.json in an OpenInference-style shape: agent, LLM, tool and merged-step spans with times, status and token counts.
          • What it covers. The website work from November 7 to 12, 2026: 68 requests and one automatic context compaction in five sessions, with 65 subagent sessions nested under the calls that started them. Some sessions ran more than once, so the dashboard counts 88 subagent runs. Unrelated work in the same sessions is left out.
          • What is never published. Prompts, responses, reasoning, tool inputs and outputs, file names and contents, and commands. A shell call carries only a category (test, build, commit and so on). Calls to tools outside an allowlist are dropped: 24 of them.
          • What is estimated. Model latency, from message timings. Tool and agent times come straight from recorded timestamps.
          • Merged spans. 1,050 of 14,718 spans are published one by one; runs of ordinary steps become summary spans that keep their step, tool-call, error and token counts. Every total, percentile and evaluator result is computed from all spans before merging.
          • No judge model. The seven evaluators are code. Nothing here is graded by an LLM, and there is no cost figure: the runs used a flat-rate subscription.
