The workflow in numbers

How it works

The build trace is a recorded run of this same workflow. One agent implements, one reviews, one verifies, and an orchestrating agent plans, delegates, integrates and commits.

The agents do real work with write access: they edit files, run tests and commit. What they know about delivery, the CI runs and source control, they read through read-only tools, so an agent can’t start a deploy or a merge by mistake. Anything that touches production waits for my approval.

When a review or a check fails, the findings come back to me. Either I correct the agent so it learns to do it properly, or I take that step over myself and hand it back as a worked example. Then the loop runs again.

In the 77 traces of this site’s build, review and verification were selective: a verifier ran in 2 of 108 delegations and a reviewer in 14, and “Review before commit” passed in only 12 of 32 scored traces.

Why I work this way

I think more of engineering will look like this: you split the work, delegate it to agents, and automate the checks around them. My time goes to the parts that need judgment: what to build, how to split it, and whether the result is right.

Delegation only works with a gate. Agents can be wrong, and they sound just as sure when they are. An edit, a test run or a commit is easy to read and undo; a production change isn’t. So the agents ask first, and I approve.

One hard decision

Each handoff between agents costs something. The receiving agent gets a summary instead of the full context, and a task that dies midway has to be handed off again.

My conclusion: keep one agent in charge of integration and commits, and add specialists where an independent check is worth more than the handoff. The multi-agent workflow I built is set up that way: one subagent implements, one reviews, one verifies, and they get read-only access to delivery tools.

One limit

In the recorded run, 8 of its 52 steps ended in an error, and 6 of those are followed by a recorded retry or fix. Both tasks that stopped midway and left partial edits behind were delegated worker tasks. One was interrupted and one lost its connection, and both were resumed.

There is no second run with more or fewer agents, so the trace cannot tell you whether this split beat one agent doing everything. The counts above show how much I use the workflow, not how well it works, and I don’t publish success or approval rates.
